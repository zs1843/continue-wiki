**检索评估**检查返回内容是否相关。**精确率（Precision）** 是返回结果中相关内容的比例；**召回率（Recall）** 是全部相关内容中被返回的比例。[1] RAG 还需要单独检查回答，不能把检索分数直接当成回答正确率。

## 用一个小集合计算

假设有一个人工核对过的小测试库，对问题 Q，相关片段只有 A、B、C；系统前三项返回 A、D、B：

| 项目 | 本例结果 |
| --- | --- |
| 返回数量 | 3 |
| 返回且相关 | 2：A、B |
| 全部相关数量 | 3：A、B、C |
| Precision@3 | 2/3 |
| Recall@3 | 2/3 |

这里 `@3` 表示只看前三项。若前四项是 A、D、B、C，则 Precision@4=3/4，Recall@4=1。扩大结果集可能找得更全，也可能带入更多噪声，不保证两个指标一起提高。

这个计算以“知道全部相关项”为前提。大资料库很难穷尽标注，报告时需要说明评估集合、相关性标准和标注范围。上述数值都是演示，不是本站检索性能。

## 回答还需要单独核对

以下是一个自拟的笔记问答评估表，帮助定位问题发生在哪一步：

| 观察 | 可检查的位置 |
| --- | --- |
| 相关章节根本没出现 | 资料是否入库、切分和检索是否漏掉 |
| 找到正确章节，答案却改变了限定条件 | 上下文组装与生成是否误读 |
| 结论正确，但引用对应别的段落 | 引用与断言的支持关系 |
| 资料不足，仍给出确定答案 | 是否能识别缺证并保留未知 |

例如原文说“测试环境允许匿名访问”，回答成“系统允许匿名访问”，可能遗漏了最关键的适用范围。检索命中该段也不能证明这条回答通过。

## 把失败样例留下来

为每个测试问题记录预期证据、可接受答案边界、实际输出和失败原因。修改切分、检索或提示后，用同一组问题比较；再补充新发现的边界问题，避免只对几个熟悉例子变好。

这是一份入门检查方法，尚不是完整评测框架。它与[软件测试反馈](/notes/testing-feedback-loops/)互补：程序能正常执行是基础，找到的证据与生成结论是否合适，还要另行判断。回到 [RAG](/notes/rag/)可以逐步定位整条链路。
