**测试反馈**是执行检查后得到、用于判断当前实现的证据。组织反馈时，需要权衡范围、速度与环境成本：较小范围的检查帮助快速定位，较大范围的检查帮助发现连接与协作问题。[1][2]

## 三种反馈范围

书中第 10.2 节按环境复杂度、执行成本与拦截目标划分三个递进环路：内环聚焦隔离的核心逻辑，中环验证服务契约与集成，外环检查系统级关键路径。[1] 下表列出各环路与配套项目材料的对应关系。

| 范围 | 主要回答的问题 | 项目中的对应材料 |
| --- | --- | --- |
| 内环：局部检查 | 隔离的核心逻辑是否正确、边界是否明确 | 折扣规则测试；架构依赖检查可作为快速结构反馈 |
| 中环：模块与边界 | API、存储与依赖适配能否配合 | Controller 集成测试、内存数据库、外部接口替身 |
| 外环：用户路径与系统协作 | 多个服务连起来后，关键流程是否可用 | Docker Compose 环境中的 Playwright 测试 |

先获得便宜、明确的反馈，再按风险扩大验证范围，可以减少每次都启动全系统的等待；只跑局部测试则可能漏掉跨系统问题。测试范围应随变更影响确定，数量本身不能说明是否充分。

作者特别要求内环避免网络、数据库和外部服务，让核心逻辑能快速反馈；中环则进入可控的集成环境，验证边界和交互；外环集中在代表业务价值的关键链路。[1] “秒、分、小时”的描述体现成本与反馈节奏的差异，不是所有工程都必须达到的固定时限。也不应把一次端到端（E2E）测试成功推广为所有边界行为均已覆盖。

## 金字塔与菱形：按缺陷分布安排投入

**测试金字塔**用较多的快速单元测试支撑较少的集成测试和端到端测试，避免把反馈都放在成本较高的系统层。**菱形测试模型**则把更多投入放到组件协作与接口契约上，两端保留核心逻辑测试和关键用户路径测试。书中用微服务边界问题解释这种重心变化。[5]

组件测试通常以一个服务为边界，检查内部模块、持久化与异常恢复；契约测试检查服务之间约定的请求、响应、错误码等是否兼容。它们回答的问题不同，接口约定相符也不等于整条业务流程已运行成功。

两种形状说明测试投入的侧重点，并未规定固定比例。规则计算复杂的模块需要充分的局部测试；经常在序列化、数据库约束或服务接口处失败的模块，需要加强边界验证。判断依据应是风险与反馈质量。

## 本地依赖：提高真实性仍需说明边界

书中第 10.3.2 节把内存数据库、容器化数据库、嵌入式服务与 HTTP 替身放在本地可控依赖的思路下讨论。[6] **Embedded** 通常表示测试期间启动的本地依赖；Testcontainers 通过容器管理依赖，WireMock 则模拟 HTTP 行为，三者的实现方式和真实性不能混为一谈。

例如，直接 Mock 仓储对象不会运行 SQL；换成数据库集成测试后，可以检查实际查询和部分约束。但 H2 通过不能自动证明 MySQL 方言与生产配置正确；用真实版本的容器也仍需检查初始化、事务和测试数据。重点是明确验证到了哪一层，而不是把“本地”理解为“完全等同生产”。

## 案例：从对象替身到协议边界

配套仓库 `chapter9/prompt.md` 提出一个重构任务：在客户 360 视图测试中，用 WireMock 替换 `CustomerCenterGatewayI` 的 Mockito 替身，并准备成功与失败的 JSON 响应文件。[3] 这是仓库中的任务材料，不是这里执行过的测试结果。

两种替身的边界不同：直接替换 Gateway 对象，可以聚焦调用它的业务；HTTP 服务替身则把替换位置移到协议边界，在测试配置与调用路径正确时，还能覆盖真实适配代码的请求构造、响应解析及错误处理。这种范围变化是对案例任务的机制解释，不意味着 WireMock 在所有情形下都优于对象 Mock。

成功和失败响应应表达明确的接口行为；若假响应与真实服务的契约不一致，测试会稳定通过，却不能证明系统能与真实服务协作。[跨系统集成案例](/notes/external-integration-case/)进一步说明了失败语义与数据边界。

## 案例：容器化端到端验证

仓库的 Compose 配置声明数据库、CRM 后端、客户中心、前端与测试执行器；服务用健康检查表达就绪状态，测试执行器在依赖服务健康后启动。[4] 这比仅等待固定秒数更直接地表达了“什么时候可以开始测试”。

E2E 工作流使用测试容器的退出码作为命令结果，并在结束时清理环境；Playwright 配置保留失败截图，在首次重试时记录 trace（可按时间回看每步操作的运行轨迹）。[4] 启动、判定与证据保存一起构成反馈链路，启动进程本身不等于测试完成。

隔离仍有边界：该示例采用固定容器名、宿主机端口与数据卷名，重复运行或并行执行需要检查资源冲突。删除测试卷也应只作用于明确的测试数据。容器化让环境更容易描述，并不自动保证所有运行彼此隔离。

## 从启动脚本到持续集成

第 10.4–10.5 节展示了环境治理的演进：先探测现状、处理冲突、启动服务、验证就绪，再将分散脚本中的环境要求放进声明式配置。[7] **环境漂移**指实际运行环境逐渐偏离预期，例如残留进程仍运行旧代码、依赖版本不同、上次测试留下数据。

端口有监听只说明有进程，不证明服务版本和业务状态正确。示例中的固定等待和按端口强杀进程也有边界：等待可能不足，端口可能属于其他任务。更稳妥的实现需要确认资源归属、设置就绪检查与超时，并限定清理范围。容器和健康检查能帮助表达这些要求，但仍需设计数据与并发资源的隔离。

**持续集成（CI）** 是在代码变更时自动构建、验证并及时反馈集成问题；**持续交付**使通过验证的变更保持可发布，**持续部署**则进一步自动进入生产。书中第 10.6 节把提交、拉取请求（PR）、合并等事件与分层检查连接，形成可追踪的验证流程。[8]

流水线文件记录何时触发、运行什么、怎样判断结果。检查失败是否真正阻止合并，还取决于仓库是否配置了必需检查或相应合并规则；不能仅因有工作流就认定已有硬门禁。测试、部署和发布也应保留各自的状态，不能把一次自动触发理解为交付成功。

## 反馈的可信度来自哪里

测试结果应能够对应到具体代码版本、环境与命令状态。[Harness 工程](/notes/harness-engineering/)需要把这些证据送回 Agent，让它依据失败原因调整行动；不能把 Agent 的“已验证”自述当成实际运行结果。

局部测试通过，不能证明全部业务路径正确；HTTP 替身也不能证明真实外部服务可用。需要明确每一层测试验证了什么，未覆盖什么。这与 [TDD](/notes/test-driven-development/)的局部开发节奏互补，也与[仓库约束](/notes/repository-constraints/)中可执行规则的作用相连。
