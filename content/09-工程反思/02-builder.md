**构建者（Builder）** 在本书的语境中，强调工程师对系统目标、实现边界和交付结果的组织责任。Agent 可以承担更多代码实现，工程师则需要表达意图、审视方案并确认验收；这是作者对人机分工变化的判断，不是所有岗位都会以同一速度变化的预测。[1]

## 构建者意味着什么

构建能力不止是把一句需求变成代码，还包括确定任务范围、组织系统关系、选择验证方式，以及为失败留下恢复路径。生成速度提高，并不会自动回答“这项功能是否应该这样做”。

例如，[客户中心集成](/notes/external-integration-case/)需要判断哪些字段以谁为准、失败时保留什么数据。这些决定必须有业务依据，不能靠模型把接口调用拼接起来后再反推需求。

## 审查为什么需要向前延伸

书中第 11.3 节强调，审视范围应扩展到产生代码的任务与约束。[2] 产物审查仍需要做，同时还应追问：目标是否明确，所需信息是否可靠，是否有规则检查和足够的反馈。

例如，同类越界修改重复出现，除了退回当前变更，还应检查任务是否写清禁止改动的范围，相关检查是否真正接入流程。这里审查的是执行条件与结果之间的关系，不是用流程审查代替对代码正确性的判断。

## 知识怎样留在组织中

作者将组织能力的沉淀与仓库中的规范、契约和检查联系起来。[2] 某个工程师知道规则，不代表后续 Agent 或新同事能够使用它。只有把规则和理由保存为可找到、可维护的材料，知识才能跨人员与会话接续。

这些材料本身也需要理解。无人维护的规则集可能继续积累[认知债](/notes/cognitive-and-architecture-debt/)，检查脚本也可能固化过时的假设。[仓库知识与约束](/notes/repository-constraints/)讨论具体载体，[Harness 套件选型](/notes/harness-kit-selection/)讨论怎样避免无目的地扩张规则。

## 生命周期的工作重心

**PDLC（产品开发生命周期）** 在书中指需求、设计、开发、测试、发布等阶段。Harness 不会使这些责任消失，而是改变人与 Agent 在其中承担的工作。[3]

| 阶段 | 需要保留的工程工作 |
| --- | --- |
| 需求 | 明确行为、边界与可验证的验收条件 |
| 设计 | 审视架构、接口及方案中的假设 |
| 开发 | 推进任务、读取反馈、处理例外 |
| 测试 | 判断测试策略、断言与覆盖是否有效 |
| 发布 | 检查门禁、运行环境与恢复安排 |

表格是对书中职责变化的归纳，不是要求每个组织采用固定职位配置。书中提出的一些时间占比和效率判断，也不能作为所有团队的实际测量结果。

**质量门禁**是以检查结果决定流程能否进入下一阶段的控制点。自动运行了 CI，并不自动代表所有发布前提都已满足；对不可自动判断的取舍，仍需有明确负责人。这里也需要[可观测性](/notes/agent-observability/)提供调查和验收的证据。
