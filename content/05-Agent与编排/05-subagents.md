**Subagent（子智能体）** 是由主流程委派、负责局部任务的 Agent。主流程组织整体目标，子智能体完成某一部分探索或处理，再交回结果供主流程整合。[1]

一种常见设计是让子代理使用独立上下文：各自在自己的窗口里检索、试错，只把压缩后的结论交回主流程。Anthropic 的多代理研究系统采用的就是「先并行探索、再压缩汇总」的方式。[1]

## 独立上下文意味着什么

独立上下文主要指模型处理任务时使用的信息范围，不代表独立的文件系统或环境。历史继承、共享文件与可用工具，取决于具体宿主的实现。

这样做的直接作用是控制主流程的上下文占用：探索过程产生的中间尝试留在子代理窗口里，主流程只接收摘要，避免长轨迹把主窗口挤满。[1]

这里常说的“上下文污染”，指无关材料、过时尝试或混杂的任务目标占据当前信息空间，干扰后续判断。隔离可以减少这些干扰，但任务说明写错、必要信息漏传，仍会影响子代理的结果；摘要也可能丢失细节。

## 分治思路与层级协作

把问题拆成子任务、分别求解、再汇总，可以借用计算机科学中的**分治思路**来理解。《Harness工程实战：从零开始驾驭AI软件工程》的相关节选也以分治和层级角色解释 Subagent。[5] Anthropic 的研究系统使用主代理规划、子代理并行探索的层级结构，是这种思路的一种应用。[1] 这是一种架构类比。多代理系统未必采用严格的递归分治算法，拆分任务也未必更快。

“首席架构师＋领域专家”可以帮助理解其中的责任分工：主代理明确总体目标、任务接口和验收要求，子代理集中处理某个局部领域，主代理核对并整合结果。清楚的职责与交接内容能减少角色混乱；仅为代理起不同的名字，并不能保证它们不重复工作。

例如，评估一次 API 变更，可以分别分析兼容性、权限边界和测试覆盖，再集中判断是否可以接受。这些分析可并行；实现修改与针对修改的最终验证则有先后依赖，需要按实际任务安排。

## 一个子代理是怎么定义的

Claude Code 用 Markdown 文件定义子代理，放在 `~/.claude/agents/` 或项目的 `.claude/agents/` 下。下面取自官方示例：[2]

```markdown
---
name: code-reviewer
description: Reviews code for quality and best practices
tools: Read, Glob, Grep
model: sonnet
---

You are a code reviewer. When invoked, analyze the code and provide
specific, actionable feedback on quality, security, and best practices.
```

frontmatter（文件开头由 `---` 包住的那段元数据）里的 `name`、`description`、`tools`、`model` 决定它叫什么、何时被选中、能用哪些工具、用哪个模型；正文是它自己的系统提示。文档说明子代理只收到这份提示和基本环境信息，不继承主代理的对话——这就是「独立上下文」在产品里的落地方式。[2]

使用时由主代理按描述委派，例如「用 code-reviewer 审查这次改动」；子代理返回结论，主代理再汇总。委派得越具体，越不容易和别的子代理重复劳动。

## 和单个代理相比

可以从上下文、并行和专注度三个方面理解多代理的收益，同时也要考虑成本。[1]

- **上下文隔离与压缩**：子代理在自己的窗口里完成检索与分析，只返回压缩后的信息，主流程不必阅读全部原始过程。
- **并行探索**：主代理可以同时启动多个子代理（文中是 3–5 个）处理不同方向；并行启动子代理与并行调用工具，让复杂查询的研究时间最多缩短约 90%。
- **专注度**：每个子代理有独立的工具、提示与探索轨迹，关注点被分开，减少路径依赖和互相干扰。

具体数字要按实验条件理解。在 Anthropic 的内部研究评测中，Opus 4 主代理加 Sonnet 4 子代理的组合，比单用 Opus 4 的代理高出 90.2%，优势集中在可以并行的广度优先任务上。[1] 该文也指出收益与 token 消耗高度相关：单个代理约为聊天的 4 倍，多代理约为 15 倍，而 token 用量本身能解释约 80% 的性能差异。[1] 换句话说，多代理常常是「花更多算力换更强能力」，不是同成本下的免费提升。

## 拆分不划算的情形

- **任务强依赖、需要共享全部上下文**：各代理必须看到同一份材料才能判断时，拆分反而增加不一致。[1]
- **多数编码任务**：真正可并行的部分少，模型对实时协调与委派也还不擅长，收益有限。[1]
- **协调与同步成本**：主代理串行等待每一批子代理时，会被最慢的一支阻塞；任务描述含糊还会导致重复劳动或漏项。[1]
- **错误沿链路放大**：子代理的结论未经核对就被汇总，错误会直接进入最终答案。

所以拆分不是默认更优。任务可并行、信息量大到单个窗口放不下、需要多种专门工具时，拆分才明显划算；其余情况先试单个 Agent 更稳。对于「整理两篇讨论同一概念的文章」这类可以独立处理的局部工作，可以分别提取定义、论据和限制，再由主流程比较异同。

## 专业化、权限与动态扩展

**专业化配置**可以针对任务选择系统指令、模型、工具和参考材料。例如，审查代理侧重找回归，检索代理侧重寻找来源。这种“调优”首先指角色与运行配置的调整，不等同于训练或微调模型权重。[2][3]

**独立权限控制**让不同角色只获得所需操作能力。OpenCode 的主代理通过权限控制可启动哪些子代理，子代理在独立子会话中使用自己的权限配置。[3] 例如，可以给审查角色只读权限；但工具权限、操作系统隔离和文件系统隔离仍是不同层面的控制。

书籍配套仓库中的 `code-reviewer.md` 就是一个实例：它描述正确性、安全性、性能与可维护性的审查职责，并禁止编辑和终端执行。[6] 文件使用较早的 `permission`、`bash` 等配置字段，说明角色设计时可以参考，但不能直接当作当前 OpenCode V2 的配置模板。[3]

**动态注册与热插拔**属于宿主的扩展机制：系统能否在运行时发现新角色、重载其配置，以及已有会话何时采用新定义，都要看实现。OpenCode 的插件文档说明了受监听目录的自动重载，也指出部分未监听依赖变更仍需重启。[4] 因此，可以把它作为选型时要核对的能力，不能从“支持 Subagent”直接推导出“所有角色都可无中断热替换”。
