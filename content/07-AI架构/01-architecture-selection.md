**架构选型** 是在动手搭建前回答两个问题：流程由代码固定，还是交给模型临场决定；在单次调用之外，还需要哪些结构，例如检索、工具、记忆或评审。它决定系统的可预测性、成本与失败方式。

## 工作流与 Agent 的分界

Anthropic 把两类系统都归为 agentic systems，但按控制路径区分：**工作流**由预定义代码路径编排模型与工具；**Agent** 由模型动态决定过程与工具使用，并对如何完成任务保持控制。[1] 选型时，控制路径比“有没有用大模型”更值得关注，因为它影响成本、可测试性和出错方式。

## 先选最简单的方案

文章的建议是寻找最简单的解，只在确有必要时增加复杂度。Agentic 系统通常用延迟与成本换取任务表现；许多应用里，带检索和上下文示例的单次模型调用已经足够。[1]

例如，假设从个人笔记里查一个概念，单次调用加检索已经能够完成。再加一层规划循环，只会增加延迟和出错面，并没有解决新问题。

## 五种常见工作流

| 模式 | 做法 | 适用条件 | 文章中的例子 |
| --- | --- | --- | --- |
| 提示链 | 固定顺序的多次调用，可在中间插入程序检查 | 子任务能清晰分解，顺序固定 | 先写文案再翻译；先列提纲、检查、再写正文 |
| 路由 | 先分类输入，再交给专门的后续任务 | 类别明确，分类本身可靠 | 客服问题分流；简单问题交小模型、难问题交大模型 |
| 并行 | 分节：独立子任务同时跑；投票：同一任务多次跑 | 子任务可并行，或需要多视角提高置信度 | 一个模型回答、另一个模型做内容审查；多次评审代码漏洞 |
| 编排者—工作者 | 中央模型动态拆解任务、派给工作者并汇总 | 子任务数量与形态无法预先确定 | 多文件代码修改；多来源检索与分析 |
| 评估者—优化者 | 一个模型生成，另一个模型评估并给反馈，循环改进 | 评估标准明确，迭代确实能带来改进 | 文学翻译；多轮检索后判断是否继续 |

并行有两种变体，用途不同：分节是把任务切开同时做，投票是把同一任务做多次再比较。评估者—优化者成立的前提是评价标准可表达，且模型能给出有价值的批评，否则循环只是重复生成。[1]

## 什么时候用 Agent

Agent 适合开放问题：步骤难以预测、无法硬编码固定路径、需要在多轮中根据环境调整，并且对模型判断有一定信任。执行中它从环境取得真实的反馈，例如工具结果或代码执行结果；可以设检查点等待人工，也常设最大迭代次数之类的停止条件。[1]

代价同样明确：自主性带来更高成本，错误可能累积；文章建议在沙箱环境充分测试，并配置护栏。客服与编程是文中两个典型场景，共同点是任务可以对话推进、有明确成功标准、能获得反馈，并且保留人工监督。[1]

## 一个选择顺序

1. 一次调用加检索能否完成？能，就停在这一层。
2. 步骤固定吗？固定时优先提示链、路由或并行。
3. 子任务数量不定、但整体结构可控？用编排者—工作者。
4. 有明确评价标准、迭代能改进？用评估者—优化者。
5. 路径无法预测、必须依赖环境反馈？才考虑 Agent。

每增加一层结构，都应说清楚它解决了什么问题，以及为此付出多少复杂度。

## 边界与常见误区

整体阅读顺序见 [AI 学习路线](/notes/ai-architecture-learning-path/)：从模型计算、资料检索、系统评估到行动边界。

- 框架会简化工具调用与串联，但抽象层可能遮蔽底层提示与响应，增加调试难度。文章建议先用模型 API 直接实现，理解之后再决定是否引入框架。[1]
- 多 Agent 不是默认答案。强依赖的任务拆开之后，交接与汇总本身会成为新的失败来源，参见 [Subagent 与任务交接](/notes/subagents/)。
- 自主性会放大 [提示注入](/notes/prompt-injection/) 与 [过度自主](/notes/excessive-agency/) 的风险，选型时需要连同权限边界一起考虑。
- 复杂度只有被评测证明有效时才值得保留，参见 [检索与回答评估](/notes/rag-evaluation-basics/) 和 [Harness 工程](/notes/harness-engineering/)。
- 文中的工具生态自 2024 年 12 月发布后已有变化，本文只取架构分类与判断依据，不把当时的框架清单当作现状。
