# 内容整理约定

note 用于收集阅读书籍、文章和其他资料时遇到的知识点，解释概念、加深理解，并通过概念之间的关联逐步形成个人知识网络。主题不限于 AI；目录按实际内容扩展，不为没有材料的领域预先填充文章。

## 正文怎样写

- 每篇围绕一个概念，或一组有明确对照关系的概念展开，让它能够成为知识网络中的稳定节点。
- 开头直接解释概念的定义、适用语境和核心含义。必要时补充机制、边界和易混淆概念，让单篇笔记能够独立阅读。
- 根据理解难度决定是否添加示例。简单概念无需硬加案例；示例应短小、服务于解释。自拟示例明确使用「例如」「假设」等表达，不写成来源中的案例或用户的真实经历。
- 用自然、清楚的概念笔记口吻。不要转录用户的选题原话，不写「原记录提到」「我先记成」「接下来想查」等整理过程自述，也不代写不存在的个人经历。
- 小标题按内容安排。定义、解释、示例、关联、参考是可用要素，不是每篇必须重复的固定章节。
- 关键论断可在段落附近注明出处，也可以用编号对应文末参考。多个来源有不同定义时，交代各自语境，不拼成一个冒充通行标准的定义。

## 来源怎样保留

优先准确理解用户提供的书或文章。需要补充解释时，可以查论文、规范、官方文档等一手材料，但要区分补充材料与原来源的观点。

- 书籍：记录实际已知的书名、作者、版本／译本，以及章节或页码；没有拿到的出版信息和页码不补猜。
- 文章／论文：记录标题、作者或机构、原文链接，必要时保留发布日期、版本与章节。
- 软件文档／项目：说明参考版本或读取日期，不把当前主分支的说明当成所有历史版本的行为。
- 区分转述、直接引文、示例与跨来源归纳。直接引用保持简短并标明出处；整理以解释为主，避免大段复制。
- 没有读到内容的资料不标「已核对」。无法确定的断言先删除、核实或保留在草稿，不用大量待查自述替代概念解释。

当前来源索引见 [来源记录](sources.md)。它记录实际使用的资料，不表示用户已经读过所有补充资料。

## 怎样形成知识网络

目录用于浏览主题，正文链接用于表达概念之间的关系。相关链接应说明为什么相关，例如前置概念、组成机制、实现实例、相似概念的区别或跨领域应用，不仅列出一串名称。

新增笔记时，优先连接已有概念；有必要时在已有笔记补充反向说明。只建立内容支持的关系，不为增加连线而堆链接。使用稳定的 `/notes/<slug>/` 地址，移动目录时保留 slug。

主题可以跨越 AI、软件工程和其他领域。跨领域术语需要说明语境，不能因为同名就视为同一个概念。后续的知识图谱或其他展示方式应建立在这些已有内容与明确关系之上。

发布前检查定义是否清楚、关键论断是否能回到来源、示例是否准确、关联是否有实际含义，再执行内容检查与构建。

## 每次整理后同步思维导图

在笔记的 `mindmap` 元数据中提炼 1–4 个关键知识点，使用正文已经解释的概念或机制；最多 8 项。节点文字保持简短，避免整段定义、参考书目和写作过程说明。需要定位到章节时，填写实际标题锚点 `heading`，不带 `#`。

新增／修改概念或章节后同步维护这些节点，再运行 `npm run build`。它会自动将公开笔记汇总到 `mindmaps/knowledge.md` 与分类导图，检查所有节点链接和章节，并生成可直接查看的站内页面。`npm run check` 会发现尚未同步的导图，单独同步使用 `npm run maps`。

思维导图是关键点的层级浏览入口，概念之间的区别、前置条件和跨领域联系继续在正文中解释并链接。生成文件不承载独立事实，不直接手工修改。使用方式见 [思维导图说明](../mindmaps/README.md)。
